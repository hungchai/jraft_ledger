## 1. Feature Overview

This document specifies two tightly coupled core mechanisms:

1. **Idempotency**: Ensures that the same ledger request (Posting / Reversal / Adjustment / Account Create) is only executed once regardless of retries, preventing duplicate payouts or duplicate bookings.
2. **Hotspot Account Concurrency**: Addresses concurrent contention on high-frequency accounts such as COMPANY_ACC in RFQ scenarios, serializing requests via an Account-Level Queue to eliminate traditional DB row lock contention.

---

## 2. Idempotency Mechanism

### 2.1 Core Principles

- **All write operations must be idempotent**: Posting, Reversal, Adjustment Approve, Account Create / Freeze / Close
- **Idempotency key**: `requestId` (UUID v7 recommended), generated by the caller and carried on every request
- **Idempotency TTL**: 24 hours (configurable); after TTL expires, the idempotency record may be evicted
- **Cross-node idempotency**: The idempotencyStore is persisted to RocksDB along with the State Machine Snapshot, so a new Leader can still recognize historical requestIds after recovery

### 2.2 Idempotency Store Design

```java
record IdempotencyEntry(
    String requestId,
    String status,          // COMPLETED / REJECTED
    String journalId,       // journalId on success
    List<String> errors,    // error code list on failure
    Instant completedAt
) {}

// In-memory store: ConcurrentHashMap (lock-free reads, Account Worker serial writes)
ConcurrentHashMap<String, IdempotencyEntry> idempotencyStore;
```

**Dual guarantee**:
- **L1**: in-memory `idempotencyStore` → P95 ≤ 0.5ms hit
- **L2**: RocksDB `CF_IDEMPOTENCY` → recovered from Snapshot on State Machine startup

### 2.3 Idempotency Check Flow

```
Client Request (requestId = req-abc123)
      │
      ▼
┌─────────────────────────────────────────┐
│ 1. Network Layer receives request       │
│    → deserialize → pre-validation       │
│    → place into request_queue           │
└─────────────────┬───────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────┐
│ 2. Account Queue Worker picks request   │
│    → idempotency check (read idempotencyStore)
│                                         │
│    IF requestId EXISTS:                 │
│      ├─ status = COMPLETED              │
│      │   → return original result (journalId etc.)
│      │   → do not execute any ledger mutation
│      │                                   │
│      └─ status = REJECTED               │
│          → return original error codes  │
│          → do not re-validate           │
│                                         │
│    IF requestId NOT EXISTS:             │
│      → continue with subsequent validation and ledger logic
└─────────────────┬───────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────┐
│ 3. State Machine apply()                │
│    → execute ledger mutation (Journal + Balance)
│    → write RocksDB WriteBatch           │
│    → idempotencyStore.put(requestId,    │
│       IdempotencyEntry(COMPLETED, ...)) │
│    → takeSnapshot() (including idempotency)
└─────────────────┬───────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────┐
│ 4. Response returned                    │
│    → first request: normal result       │
│    → retry request: cached result (same path)
└─────────────────────────────────────────┘
```

### 2.4 Idempotent Behavior per Write Path

| Operation | Idempotency Key Field | Duplicate Request Behavior | Error Code |
|---|---|---|---|
| Posting | `requestId` | Return original Journal (HTTP 200) | — |
| Reversal | `requestId` | Return original Reversal Journal (HTTP 200) | — |
| Adjustment Approve | `requestId` | Return original Adjustment Journal (HTTP 200) | — |
| Account Create | `requestId` | Return original Account (HTTP 200) | — |
| Account Freeze | `requestId` | Return original operation result (HTTP 200) | — |

**Notes**:
- Adjustment **Draft creation** (Maker submission) does not go through Raft; idempotency is guaranteed by the MySQL `adjustments_draft` table `draftRequestId` UNIQUE constraint
- Idempotency records remain valid after Raft Leader switch (recovered from RocksDB Snapshot)

### 2.5 Idempotency After Raft Leader Failover

```
Scenario: Client sends Posting → Leader receives → apply completes → Leader crashes before returning Response
       → Client retries on timeout → New Leader elected

New Leader behavior:
  1. Recover State Machine from RocksDB CF_SM_SNAPSHOT
     → idempotencyStore contains req-abc123 → COMPLETED
  2. Client retry reaches New Leader
  3. Account Queue Worker checks idempotencyStore
     → hit → return original result → do not re-execute

Result: No duplicate posting; client eventually receives success
```

### 2.6 Idempotency TTL and Eviction

```
Purpose: Prevent unbounded growth of idempotencyStore (millions of requestIds)

Strategy:
  - Default TTL: 24 hours (config item `ledger.idempotency.ttl-hours`)
  - Eviction Job: scan hourly and delete records where completedAt + TTL < now
  - RocksDB: CF_IDEMPOTENCY uses TTL column family for automatic expiration

Safety boundary:
  - Retry within 24 hours → idempotency effective
  - Retry same requestId after 24 hours → treated as new request, may duplicate
  - Business side should ensure retries complete within a reasonable window
```

### 2.7 Relationship Between Idempotency and Concurrency

```
Scenario: Two threads simultaneously send the same requestId

Handling:
  Thread-A reaches Account Queue first → checks idempotencyStore → miss
  Thread-A enters State Machine apply()

  Thread-B reaches Account Queue simultaneously → checks idempotencyStore → miss
  (because Thread-A has not yet completed apply)

  Thread-A completes apply → idempotencyStore.put(requestId, COMPLETED)
  Thread-B enters apply → checks idempotencyStore again → hit COMPLETED
  Thread-B returns cached result

  Result: Only one ledger mutation executed (Thread-A), Thread-B returns same result

Key guarantee: Account Queue is single-threaded serial, so the above race cannot happen for the same account.
Multi-account (RFQ) races are handled by the Multi-Account Coordinator token mechanism.
```

## 3. Hotspot Account Concurrency Handling

### 3.1 Problem Definition

```
RFQ scenario:
  CLIENT_ACC_001 ──→ COMPANY_FX_ACC
  CLIENT_ACC_002 ──→ COMPANY_FX_ACC
  CLIENT_ACC_003 ──→ COMPANY_FX_ACC
  ...
  All client RFQ trades have the same COMPANY_FX_ACC as counterparty

Traditional solution problems:
  - Multiple threads simultaneously UPDATE COMPANY_FX_ACC balance → DB row lock contention
  - Under high concurrency, lock wait time grows linearly, P95 cannot be met
  - Lock escalation and deadlock risk
```

### 3.2 Solution: Account-Level Queue

```
Each accountId maintains an independent LinkedBlockingQueue:

AccountQueueManager
  ├── queue("CLIENT_ACC_001") → Virtual Thread Worker-1
  ├── queue("CLIENT_ACC_002") → Virtual Thread Worker-2
  ├── queue("COMPANY_FX_ACC") → Virtual Thread Worker-3   ← hotspot
  ├── queue("CLIENT_ACC_003") → Virtual Thread Worker-4
  └── ...

Queue characteristics:
  - Single Virtual Thread consumer (Java 21 Virtual Threads)
  - All requests for the same account are strictly serialized
  - Queues for different accounts execute in parallel (no mutual blocking)
```

### 3.3 Why Lock Contention Is Eliminated

```
Traditional DB row lock:
  Thread-A ──→ UPDATE COMPANY_FX_ACC balance = balance + 100
  Thread-B ──→ UPDATE COMPANY_FX_ACC balance = balance - 200
  Thread-C ──→ UPDATE COMPANY_FX_ACC balance = balance + 300
  → Three threads compete for the same row lock; later arrivals wait

Account-Level Queue:
  Thread-A ──→ enqueue to queue("COMPANY_FX_ACC")
  Thread-B ──→ enqueue to queue("COMPANY_FX_ACC")
  Thread-C ──→ enqueue to queue("COMPANY_FX_ACC")

  Worker-3 (single Virtual Thread):
    1. Pick Thread-A request → apply → balance + 100
    2. Pick Thread-B request → apply → balance - 200
    3. Pick Thread-C request → apply → balance + 300

  → No lock contention, only nanosecond-level queue enqueue/dequeue latency
  → All COMPANY_FX_ACC operations are serialized in memory
```

### 3.4 Multi-Account Atomic Coordination (RFQ Scenario)

```
Problem: RFQ involves two accounts (CLIENT_ACC + COMPANY_ACC); how to guarantee atomicity?

Solution: Multi-Account RaftCommand Coordinator

Phase 1 — Acquire coordination tokens (sorted by accountId ascending to avoid deadlock):
  1. Collect all involved accountIds
  2. Sort in lexicographically ascending order (CLIENT_ACC_001 < COMPANY_FX_ACC)
  3. Sequentially acquire a "Coordination Token" in each Account Queue
  4. After all queues have tokens, enter Phase 2

Phase 2 — Build and submit Multi-Account RaftCommand:
  1. Build a single RaftCommand containing all JournalLines
  2. Submit to Raft Group → Quorum commit
  3. State Machine apply updates in-memory balances for all accounts at once
  4. Treated as atomic: all succeed or all fail

Phase 3 — Release tokens:
  1. Release each Account Queue's Coordination Token in ascending order
  2. Other requests can continue

Deadlock prevention:
  - Key: all Multi-Account operations acquire tokens in the "same order"
  - If two RFQs both involve A+B, both acquire tokens in A→B order
  - No cyclic wait such as RFQ-1 holding A and RFQ-2 holding B
```

### 3.5 Back-Pressure

```
When Account Queue depth exceeds the threshold, reject new requests:

Config:
  ledger.account-queue.max-size = 10,000 (default)

Behavior:
  IF queue("COMPANY_FX_ACC").size() >= MAX_QUEUE_SIZE:
    → return HTTP 429 QUEUE_FULL
    → caller should retry with exponential backoff

Purpose:
  - Prevent unbounded memory growth (OOM)
  - Prevent extreme concurrency from causing single-queue backlog
  - Signal caller to slow down

Monitoring:
  - Metric: ledger.state_machine.queue.depth (Gauge, accountId dimension)
  - Alert: queue depth > 5,000 for 2 minutes → PagerDuty
```

### 3.6 Performance Comparison

| Scenario | Traditional DB Row Lock | Account-Level Queue |
|---|---|---|
| Single hotspot account 1000 QPS | P95 ≈ 50–200ms (lock wait) | P95 ≤ 3ms (pure in-memory) |
| Lock contention | High (linear growth) | None (serialization) |
| Deadlock risk | Exists (requires detection/timeout) | None (single-threaded) |
| Scalability | Vertical scaling (DB CPU) | Horizontal scaling (add nodes) |
| Memory overhead | Low | One queue per account (~KB level) |

### 3.7 Virtual Thread Scheduling

```java
// Each Account Queue corresponds to one Virtual Thread
Thread.startVirtualThread(() -> {
    while (running) {
        Command cmd = queue.take();  // blocking wait
        try {
            stateMachine.apply(cmd);   // serial execution
        } catch (Exception e) {
            logger.error("Apply failed", e);
        }
    }
});
```

**Design rationale**:
- Virtual Threads are lightweight (~KB stack), allowing hundreds of thousands
- Blocking operations (queue.take()) do not occupy OS threads; scheduled by JVM
- Context switch cost is extremely low compared to Platform Threads

## 4. Synergy Between Idempotency and Hotspot

```
Complete RFQ concurrency + retry scenario:

Step 1: Client sends RFQ Posting (requestId = req-001)
         → reaches Leader → enqueue to queue("CLIENT_ACC_001")
         → enqueue to queue("COMPANY_FX_ACC")

Step 2: At the same time, another Client sends RFQ Posting (requestId = req-002)
         → enqueue to queue("CLIENT_ACC_002")
         → enqueue to queue("COMPANY_FX_ACC")

Step 3: queue("COMPANY_FX_ACC") Worker serially processes:
         First execute req-001 (update COMPANY_FX_ACC balance)
         Then execute req-002 (update COMPANY_FX_ACC balance)
         → No lock contention, no data race

Step 4: Client retries req-001 due to network timeout (same requestId)
         → idempotencyStore hit → return original result
         → Do not update COMPANY_FX_ACC again

Result:
  - Concurrency safety: guaranteed by Account Queue serialization
  - Idempotency safety: guaranteed by idempotencyStore
  - Performance target: P95 ≤ 3ms
```

## 6. Acceptance Criteria

| # | Acceptance Condition | Test Method |
|---|---|---|
| AC-01 | Retrying the same requestId 1000 times only creates 1 Journal | Idempotency Test |
| AC-02 | Idempotency retry hits idempotencyStore with P95 ≤ 1ms | Performance Test |
| AC-03 | After Raft Leader switch, retrying a historical requestId still returns the original result (no re-execution) | Failure Recovery Test |
| AC-04 | 1000 concurrent RFQs targeting the same COMPANY_ACC: no duplicate payouts, no balance inconsistency | Concurrency Safety Test |
| AC-05 | 1000 concurrent RFQs targeting the same COMPANY_ACC: Posting P95 ≤ 3ms | Performance Test |
| AC-06 | When Account Queue depth exceeds MAX_QUEUE_SIZE, return QUEUE_FULL | Backpressure Test |
| AC-07 | Multi-Account coordination acquires tokens in accountId ascending order; no deadlock | Deadlock Stress Test |
| AC-08 | After idempotencyStore exceeds TTL, auto-eviction treats new requests as first-time | TTL Test |
| AC-09 | After Virtual Thread Worker crash, Account Queue auto-rebuilds and resumes consumption | Failure Injection Test |
| AC-10 | Two simultaneous identical requestIds: only one ledger mutation is executed | Race Condition Test |

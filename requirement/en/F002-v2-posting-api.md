# F-002 v2 Posting API — Batch Atomic Posting (Raft Architecture Update)

**Document Version**: v0.4 (Added `position` field to JournalLine — supports CURRENT/LOCKED/FROZEN sub-balance types)  
**Feature**: F-002 Posting API  
**System**: Next-Gen Internal Ledger Platform  
**Status**: Draft for Review  
**Change Summary**: Write path changed from direct PostgreSQL writes to Raft State Machine; balance validation changed from DB reads to in-memory reads; v0.4 adds `position` field for sub-balance types

---

## 1. Architectural Prerequisites (per ADR-001)

- **Write Path**: All Posting requests are serialized by the Account-Level Queue on the Raft Leader node. The State Machine updates in-memory balances and persists to RocksDB.
- **No Direct DB Writes**: The Posting write path does not touch MySQL at all; MySQL is asynchronously synced by the Learner for queries.
- **Balance Validation**: Reads from the in-memory State Machine, not the DB, with P95 ≤ 2ms

---

## 2. Feature Overview

The Posting API accepts ledger requests containing one or more legs. These are executed atomically on the Raft Leader node: double-entry generation, balance validation, State Machine updates, RocksDB persistence, and asynchronous sync to the MySQL View Layer via the Learner.

## 3. Request Structure

### 3.1 Top-Level Request Body

| Field | Type | Required | Description |
|---|---|---|---|
| `requestId` | `string` | ✅ | Idempotency key, globally unique (UUID v7 recommended) |
| `businessEventType` | `string` | ✅ | Business event type, e.g. `RFQ_SETTLEMENT`, `WITHDRAWAL`, `FEE` |
| `businessEventRef` | `string` | ✅ | Upstream business event ID |
| `valueDate` | `date` | ✅ | Ledger effective date |
| `legs` | `list<Leg>` | ✅ | At least one leg; each leg contains two JournalLines (debit + credit) |
| `metadata` | `map<string,string>` | ❌ | Extension fields, e.g. traceId, operator ID |

### 3.2 Leg Structure

| Field | Type | Required | Description |
|---|---|---|---|
| `legId` | `string` | ✅ | Unique ID for this leg (generated by caller) |
| `postingType` | `string` | ✅ | Posting type, e.g. `TRADE_SETTLEMENT`, `FEE`, `INTEREST` |
| `amount` | `decimal` | ✅ | Amount for this leg, must be > 0; all lines share this amount |
| `currency` | `string` | ✅ | ISO 4217 currency code; all lines share this currency |
| `lines` | `list<JournalLine>` | ✅ | Must contain at least one DEBIT + CREDIT pair; amount and currency specified at leg level |

### 3.3 JournalLine Structure

| Field | Type | Required | Description |
|---|---|---|---|
| `accountId` | `string` | ✅ | Target account |
| `balanceType` | `string` | ✅ | Must exist in the Balance Type Registry (F-001) |
| `position` | `string` | ✅ | Sub-balance position: `CURRENT` (available), `LOCKED` (held), `FROZEN` (suspended) |
| `entryType` | `enum` | ✅ | `DEBIT` / `CREDIT` |
| `description` | `string` | ❌ | Journal line description |

### 3.5 Sub-Balance Position Examples

The `position` field distinguishes different sub-balance states within the same `balanceType`:

| Position | Description | Use Case |
|---|---|---|
| `CURRENT` | Available balance | Normal trading, withdrawals, transfers |
| `LOCKED` | Locked balance | Pending settlements, pre-authorizations |
| `FROZEN` | Frozen balance | Compliance holds, dispute resolution |

## 4. Validation Rules

### 4.1 Pre-Validation (Network Layer, before entering Raft)

| # | Rule | Error Code |
|---|---|---|
| V-01 | `requestId` format is valid | `INVALID_REQUEST_ID` |
| V-02 | `legs` contains at least one leg | `LEGS_EMPTY` |
| V-03 | All `balanceType` values in each leg must exist in the Registry and be ACTIVE | `BALANCE_TYPE_NOT_FOUND` |
| V-04 | Leg `amount` must be > 0 | `INVALID_AMOUNT` |
| V-05 | Each leg must have at least 2 lines (at least one DEBIT + one CREDIT) | `JOURNAL_UNBALANCED` |
| V-06 | Each line's `position` must be `CURRENT`, `LOCKED`, or `FROZEN` | `INVALID_POSITION` |

### 4.2 Idempotency Validation (Account Worker, in-memory)

| # | Rule | Result |
|---|---|---|
| V-07 | `requestId` already exists and is `COMPLETED`; return original result directly | Idempotent success |
| V-08 | `requestId` already exists and is `PROCESSING`; return `409 PROCESSING` | Retry pending |

### 4.3 Business Validation (State Machine, in-memory balance)

| # | Rule | Error Code |
|---|---|---|
| V-09 | Every involved account must exist | `ACCOUNT_NOT_FOUND` |
| V-10 | The corresponding balanceType + position + currency for each account must be initialized | `BALANCE_NOT_INITIALIZED` |
| V-11 | For balances with `allowNegative=false`, DEBIT must not result in a balance below 0 | `INSUFFICIENT_BALANCE` |
| V-12 | For balances with `allowNegative=true` (e.g. `TRADE_AHEAD_BALANCE`), CREDIT must not result in a balance above 0 | `CREDIT_EXCEEDS_LIMIT` |
| V-13 | For `position = LOCKED` or `FROZEN`, balance cannot go negative | `LOCKED_BALANCE_CANNOT_BE_NEGATIVE` |
| V-14 | Account is not frozen (`account.status = ACTIVE`) | `ACCOUNT_FROZEN` |

## 5. Execution Flow (Raft Write Path)

```
1. [Network Layer]
   Receive HTTP request → Deserialize → Pre-validation (V-01 ~ V-05)
   → Enqueue into request_queue

2. [Ledger Layer]
   Dequeue from request_queue
   → Sort all involved accountIds in ascending order (deadlock prevention)
   → Route to respective Account Queues

3. [Account Queue Coordinator]
   Wait for all involved account queues to be ready (Multi-Account coordination)
   → Idempotency validation (V-06 ~ V-07)
   → Business validation (V-08 ~ V-12, reading in-memory State Machine)
   → Build RaftCommand (containing all JournalLines)

4. [Raft Layer]
   Submit RaftCommand to Raft Group
   → Leader writes Raft Log
   → Replicate to Followers (commit upon reaching Quorum)

5. [State Machine Apply]
   Apply Raft Log:
   a. Generate Journal (journalId, journalType=NORMAL)
   b. Generate all JournalLines (including balanceBefore, balanceAfter)
   c. Atomically update in-memory balances for all involved accounts
   d. Write to RocksDB (journal + balance, WAL guarantees durability)
   e. Update in-memory idempotency map (requestId → result)

6. [Learner Async Sync]
   Learner listens to Raft Log
   → Asynchronously writes to MySQL journal_line, account_balance (View Layer)

7. [Response]
   Return result to client via response_queue
```

## 6. Multi-Account Atomicity (RFQ Scenario)

RFQ involves two accounts: CLIENT_ACC + COMPANY_ACC (hotspot):

```
Traditional problem:
  CLIENT_ACC is in Account Queue A
  COMPANY_ACC is in Account Queue B
  How to guarantee atomicity across queues?

Solution: Multi-Account RaftCommand

1. Sort involved accounts by accountId in ascending order (CLIENT_ACC_001 < COMPANY_FX_ACC)
2. Acquire a "coordination token" in each Account Queue in sequence
3. Once both queues are ready, build a single RaftCommand containing all legs
4. When RaftCommand is applied in the State Machine:
   - Update all account in-memory balances in one shot
   - Treated as an atomic operation
5. Any single account validation failure → entire RaftCommand is rejected; all account balances remain unchanged
```

COMPANY_ACC is a hotspot, but because all requests are serialized within the same Account Queue, **there is no lock contention, only nanosecond-level queue waiting**.

## 8. Performance Targets (per ADR-001)

| Metric | Target | Rationale |
|---|---|---|
| Posting P95 | ≤ 3ms | No MySQL access; pure in-memory + RocksDB WAL |
| Balance Validation P95 | ≤ 0.5ms | Direct read from in-memory State Machine |
| Hotspot Account (COMPANY_ACC) | Same as regular accounts | Account Queue serializes requests; no DB row lock contention |
| Idempotent Retry P95 | ≤ 1ms | In-memory idempotency map hit |
